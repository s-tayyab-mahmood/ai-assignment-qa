# Automation Exercise: Playwright QA with AI-assisted RCA

A Playwright + TypeScript test automation solution for [automationexercise.com](https://automationexercise.com) with:
- risk-based UI, API and integration tests
- isolated test data that is cleaned up after every test
- GitHub Actions CI (daily at 05:00 PKT, on pull requests, and on demand)
- a deterministic failure-diagnostics pipeline, with an optional, guarded AI root-cause-analysis step
- a self-healing agent that proposes validated fixes for stale locators and test-oracle mistakes – a human reviews and applies every fix

## Quick start
```bash
nvm use 22                 # Node.js LTS (22.x)
npm ci
npx playwright install --with-deps chromium
cp .env.example .env       # optional; defaults work without it
npm run verify             # typecheck + lint + list tests
npm run test:smoke         # fast critical subset
npm test                   # everything (api, ui, integration)
npm run report             # open the HTML report
npm run rca                # build failure bundle + RCA summary → reports/rca/
```

## CI
The workflow is `.github/workflows/playwright.yml`.
- **Triggers:**
  - `schedule: '0 0 * * *'` (05:00 Asia/Karachi; Pakistan has no DST). It runs only from the **default branch**, and GitHub may start it a few minutes late.
  - `pull_request` to `main`
  - `workflow_dispatch`, with an optional grep and an option to skip the health check
- **Site health check:** before the tests, CI probes the home page and the products API. If the site is overloaded or slow (>10 s), it waits 10 min and tries again, up to 4 attempts (pull requests: 1 attempt). If the site recovers, tests run; if not, the job fails with "Site unavailable – tests were not run" and the probe table in the job summary. Run it locally with `npm run health`.
- **Status propagation:** the test step records its outcome. Diagnostics run with `if: always()` and `continue-on-error`, and the final step fails the job only if the tests failed. This means AI or report problems cannot hide a test failure or fake a pass.
- **Artifacts:** the `qa-report-<run_id>-<attempt>` artifact contains:
  - the HTML, JSON and JUnit reports
  - traces, videos and screenshots
  - `reports/rca/*`

  The RCA summary is also written to the job summary.
- **Secrets:**
  - `AI_API_KEY` (optional) – key for the AI provider; add it under repo Settings → Secrets → Actions. Default provider: Google Gemini free tier (key from Google AI Studio, no card).
  - It is **never passed to `pull_request` runs**. PR runs get the model-free RCA.
  - Optional repository variables: `AI_PROVIDER` (`gemini` default, or `anthropic`), `AI_MODEL` (currently `gemini-3.6-flash`), `AI_TIMEOUT_MS` (default 30000, max 60000).
- **Site safety:** 2 workers, 1 retry in CI, one run per ref at a time.

## AI-assisted RCA in short
1. `collect`: test results become `failure-bundle.json`. The bundle contains each failure's error, stack top, attempts, trace/screenshot paths, network and console logs, cleanup log, fault-injection annotation, changed files, commit and run URL. Everything is redacted.
2. `classify`: rules produce competing hypotheses with evidence for and against, a calibrated confidence, owner, severity and next action. Weak evidence gives UNKNOWN.
3. `ai` (optional): sends sanitized evidence wrapped as untrusted data. The output must pass a schema check and evidence-ID checks, and it can never call an injected fault a product defect. If the AI disagrees with the rules, confidence is capped at 0.6.
4. Publish: `rca-report.json`, `rca-summary.md` and `audit-log.jsonl`. Every record is `HYPOTHESIS_PENDING_REVIEW` and requires human approval.

The details are in `skills/rca.md`, `docs/architecture.md` and `docs/ai-policy.md`.

## Self-healing agent in short
After RCA on a failed run, the agent decides whether a failure may be healed at all, finds a one-line fix, proves it and hands it to a human:
1. **Policy:** only `LOCATOR_OR_UI_CHANGE` / `TEST_SCRIPT_DEFECT` (confidence ≥ 0.5). Product defects, environment, timing, data, flaky and injected faults are declined – healing them would hide a real problem.
2. **Fix:** a stale locator is matched against the page's accessibility snapshot at failure (rules first; AI only as a fallback and only from elements that were on the page). A test-oracle mistake gets an AI-proposed one-line change, labelled ⚠️ ASSERTION_CHANGE.
3. **Proof:** type check, lint and 3/3 isolated runs of the failing test, or the change is discarded.
4. **Hand-over:** a patch in the `qa-report` artifact (`reports/heal/patches/`) and a job-summary section. Nothing is committed or pushed; the reviewer applies it with `git apply` on a branch and opens a PR.

Details: `skills/self-healing.md`, `agents/orchestrator.md` (agent 5), `docs/fault-injection/FI-04.md`.

## Code quality gates
Strict TypeScript (`strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`); ESLint with `typescript-eslint` and the Playwright plugin, including **type-aware promise rules** (`no-floating-promises`, `await-thenable`, `no-misused-promises`) so a missing `await` fails CI; Prettier format check on code and config; Zod validation of API responses at runtime. `main` is protected against force pushes and deletion; changes from agents arrive through a reviewed PR.

## Limitations and known risks
- **Live-site variability.** The public site is sometimes slow or overloaded (HTTP 503 "heavy load", requests held >25 s). Such failures are classified ENVIRONMENT_OR_NETWORK by RCA rather than "fixed" in tests; local runs use `WORKERS=1`. The first live runs also exposed five test-code defects, all fixed and documented (`docs/evidence/`, `docs/ai-evidence/prompt-log.md` Part B).
- **RCA accuracy.** On real failures, the rule-based RCA's first verdict was right in 24 of 36 cases (3 of 11 in the first live runs, improving as corrections became rules); every miss was caught in human review and turned into a rule plus a regression case (`docs/scorecard.md`). Classifications always require human approval.
- **AI provider.** Default is the Google Gemini free tier (rate-limited; free-tier data may be used for training, so prompts carry only redacted synthetic evidence). Provider overloads and timeouts fall back to the rule-based result (`docs/ai-evidence/ai-rca-runs.md`).
  - Most likely spots: the address block format (AE-15/16), the invoice text format (AE-17), the brand-sidebar count span (AE-10), and the recommended carousel (AE-21).
- **Ads are blocked** by host pattern. If the site adds new ad hosts, extend `blockedThirdPartyHosts`.
- **Public shared site:** availability and content can change. That is handled by RCA, not by weakening tests.
- **Schedule timing is best-effort.** GitHub may start scheduled runs late under load. The first scheduled run (2026-11-20) was due at 05:00 PKT (00:00 UTC) and started at about 10:20 PKT (05:20 UTC); on 2026-11-26 it started at 11:27 PKT (06:27 UTC). On-the-hour schedules are the most delayed, but the brief fixes 05:00, so the time is kept and the delay documented. Use `workflow_dispatch` when a run is needed at a specific time.
- **Chromium only;** no visual or accessibility audits. See docs/test-strategy.md §8.
- **Evidence must be real.** The FI reports, scorecard, traceability status and approvals are deliberately left blank until they are filled from real runs.
